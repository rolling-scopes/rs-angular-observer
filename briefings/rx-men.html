elrouss — Team Lead · 66 commits · 34 PRs (32 merged)

Built (grounded in PR titles + diary):

  • Home Page — full responsive composition: hero block, promo section, product sections, carousel integration, shared footer, autofocus directive for search.
  • Sprint 2 diary explicitly names reviewing 5 PRs in a row to keep team throughput moving.
  • PR #123: stub auth and products services scaffolded ahead of commercetools integration.
  • Established code review etiquette document: nit / question / praise tags, thread closure rules.

Level: Noticeably above cohort average. Thinks in systems: centralised test-id registry (app.test-ids.ts), design tokens adapted from Tailwind scales, GitFlow enforced via rebase (diary: "real risk of breaking linear git history, but I managed to straighten it out"). Writes reflective, technically precise diaries (40–45 h per sprint, documented). Knows when a library is too heavy and builds natively (Carousel decision discussed with mentor, rationale documented).

Risks / watch points:

  • commercetools integration not started as of sprint 2, despite being in sprint 1 plans. May be carrying too much scope.
  • Diary openly notes "uneven team velocity" and concern that Cart page scope may need reassignment. He knows it; probe whether he has a mitigation plan.
  • Heavy on process governance (board labels, epics, Kanban columns) — verify this translates to actual product delivery in sprint 3.

Probe at interview: Ask him to explain the Carousel component architecture from scratch — why native instead of a library, how autoplay and responsive scaling are handled, what trade-offs remain. Then ask about the CI/CD pipeline design choices (why commitlint + branch validation, not just lint). Both are his own work with documented rationale; if he can articulate the why, that confirms understanding. The Carousel is the most interesting can-you-build-it test because it required a deliberate library rejection.

Level: Honest and self-aware in diary; this is the most reliable signal. Sprint 2 diary: "Main problem — understanding where Angular ends and my React habits start." Worked through CVA vs model() decision himself, documented the rationale (YAGNI applied correctly). Understands touched vs dirty distinction after struggling with it. Knows why CVA exists ("you start to understand why CVA exists at all"). Low commit count (8) likely reflects feature-branch commits not yet landing in main rather than passivity, but the signal is still lower than the lead.

Risks / watch points:

  • Only 8 commits over ~5 weeks is thin. If the feature branch work does not merge before the interview, the raw number will look passive.
  • Sprint 2 ends the diary with "writing code is fun, but answering questions — not sure I enjoy that, and it's coming soon." Self-aware, but it means interview nervousness is real. Calibrate probing accordingly — go specific, not broad.
  • No diary mention of actually integrating Sign Up with the backend or routing guards beyond the confirm() placeholder.

Probe at interview: Ask him to explain the Sign Up form architecture — specifically, why a form-level validator for password confirmation rather than a field-level one, and what touched vs dirty means in that context. His diary shows he genuinely worked through this. Then push on the navigation guard: the confirm() is a placeholder — what would the real implementation look like and why does the current one not work with a custom modal? This is a clean test of depth vs. surface knowledge.

No routing beyond lazy loading, no forms, no state management, no API integration touched. Diaries mention code review iterations (2–3 cycles per component) but the components themselves are simple enough that multiple review passes on an Empty component is a warning sign rather than evidence of depth. diary sprint 1 is surface-level (bullet points, no technical reflection). Sprint 2 diary is more detailed about the TeammateCard but still primarily describes what was done, not why decisions were made.

Risks / watch points (serious):

  • About page PR #108 is open and has been in progress for a long time — a static content page. This is a velocity signal that cannot be explained away.
  • Sprint 1 diary: "Initially hardcoded the icon, then understood the component should be more flexible" — that's a very basic Angular input API lesson for sprint 1. Expected much earlier from any Angular learner.
  • No evidence of working with forms, state management, services, routing guards, or API calls in either sprint.
  • Elrouss's sprint 2 diary explicitly calls out "tasks that should have been relatively straightforward — 404 and About pages — were moving for up to two weeks." Denis owns both of those.

Probe at interview (calibrate expectations, but probe honestly): Ask him to explain the flip-card component: how does focus-within work in CSS and why is it the right approach for keyboard accessibility vs. just hover? This is the most technically specific thing he did. Then ask: what would it take to connect the About page content to a CMS or a backend API instead of a static JSON file — walk through the Angular service, injection, and component binding steps. This probes whether he understands the Angular data flow beyond static rendering. If he cannot describe this, it is evidence the gap is conceptual, not just time-based.

Conclusion for the mentor

Overall readiness: Below average for a 2-sprint team. The product is moving (deployed, Home Page visible, Sign Up form built) but almost entirely on the back of one person. Lead (elrouss) is carrying infra, UI kit, Home Page, code review, board governance, and team coordination simultaneously. That is unsustainable and he knows it — his diary is a candid project manager's log of a team that isn't self-driving.

Who is strong: elrouss without question. Technically deep, articulate, thinks in systems, documents his reasoning. Would do well individually. The interview risk with him is that he is so fluent he may appear stronger than he is on commercetools/state management topics he hasn't actually built yet — probe those gaps specifically.

Who is growing: prokhorovd is a genuine middle. Honest self-assessment, correct Angular instincts emerging (CVA vs. model() decision, touched vs. dirty), building meaningful form components. Low commit count is a concern but his diary shows real engagement. Likely will perform credibly if the interview is specific to the work he actually did.

Who to watch: den987655. Slow delivery (About page still open), narrow scope (UI-only, no Angular data layer touched), limited technical reflection in diaries. Sprint 1 defence score of 75 is higher than the repo activity alone would predict — the mentor (home mentor mummick) may have weighted engagement and verbal explanation. The cross-interview is the first independent calibration. Do not let the flip-card card trick fill the interview time; get to Angular services and data flow.

Recommended interview angle:

  • elrouss: go deep on Carousel (native build decision) and CI/CD design. Ask about the commercetools integration plan — what is blocked, what is the first API call he would make. Probe whether he has a realistic plan for sprint 3 or is still spreading across too many epics.
  • prokhorovd: Sign Up form architecture (form-level validator reasoning, touched vs. dirty, navigation guard placeholder and what the real solution looks like). Go slow — he is nervous about interviews and will warm up if questions are concrete.
  • den987655: TeammateCard accessibility (focus-within vs. hover) and then force a data-flow question (service → component → template) to test whether he understands Angular beyond template rendering. Set expectations accordingly.
