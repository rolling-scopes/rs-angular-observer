Student profiles

dusixx — team lead, 179 commits / 24 merged PRs

Built (from PRs + diary):

  • Full repo setup: Angular 22 scaffold, path aliases, ESLint/Stylelint/Prettier/commitlint config, Husky hooks (commit-msg, pre-commit, pre-push), PR template, branch protection rules. Spent ~4–5 h on this.
  • Custom button: started as an attribute directive (v1), rebuilt to attribute component (v2 during Sprint 3 after mentor suggestion). v1 used Renderer2 in the directive to inject spinner and icon elements; handled width-locking via afterRenderEffect + getBoundingClientRect().width; tracked button text content via afterEveryRender to toggle no-text class. The journey from ngAfterViewChecked + requestAnimationFrame to proper render hooks is documented in his diary — this shows real exploration.
  • Main layout: responsive sidebar (resizable via angular-split library), BreakpointService with three breakpoints (mobile/tablet/desktop), mobile drawer with model() two-way binding between header and menu.
  • CSS theming: replaced atomic color tokens with semantic --color-text, --color-surface etc.; Taiga UI variable overrides.
  • Routing: lazy-loaded routes for login/signup/wildcard with guestGuard.
  • Angular 22 upgrade (update/ng-22 PR merged 2026-06-09): resolved ESLint conflicts, decided to move to signal-style forms and resources.
  • Auth pages (Sprint 3, merged 2026-06-14): Signal Forms signup/login with native validators (required, minLength, pattern, custom validate() for confirm-password). Server error shown on form and cleared on any field change — implemented as a standalone function using effect() on form signal + error signal. Taiga UI tui-textfield invalid-mode override via a custom MutationObserver directive to prevent premature invalid state on required validator.
  • Discover page, track card UI.

Level: Technically strong and reflective. He documents his wrong turns (button v1 → v2, raf → afterRenderEffect, ngAfterViewChecked → afterEveryRender). He reasons about trade-offs rather than just picking the first working solution. The model() two-way binding example and the error-clearing effect() pattern both show Angular signal understanding beyond "copy from docs." Heavy reliance on angular-split for the resizable sidebar and Taiga UI for form fields — those are valid choices, but they black-box key interactions.

Probe at interview: The button rebuild is the gold vein. Ask him to implement a loading button from scratch (attribute component on a native <button>) — can he place the spinner in the right slot, lock width without requestAnimationFrame, and not trigger change detection unnecessarily? His diary traces every mistake; if he can reconstruct the solution, he understands it. Secondary probe: the MutationObserver directive for Taiga's data-mode='invalid' override — why did he need it, what is it watching, what would break without it? That's an Angular + DOM + library interaction that is genuinely non-trivial and clearly his own work.

Probe at interview: The Firebase auth race condition is the strongest evidence of real problem-solving. Conclusion for mentor

Overall readiness: Above average for the sprint count. Two active students, no passenger, both writing substantive diaries. The team self-organised a three-state auth model, migrated to Angular 22 mid-course, set up real CI/CD, and has a live deploy.

Balance: dusixx carries more volume and complexity (179 commits, the complex button and layout system) but inalitvinka is not far behind (158 commits) and owns real architectural pieces: CI/CD from zero, Firebase auth with proper async guard, Firestore data layer. Risks to probe:

  1. Library reliance (Taiga UI, angular-split, Firebase SDK): both students work at the integration level for some features. Taiga UI wraps a lot — the button's MutationObserver workaround exists precisely because Taiga UI's validation state clashed. Check they understand the Angular underneath, not just the library surface.
  2. ngInit dropout: a third student contributed to Sprint 1 (layout/header/footer) and then vanished. Both remaining students absorbed the workload and didn't stall, but the roster has an unresolved situation. Mention it if the mentor needs to check official enrollment status.
  3. Open PR risk: inalitvinka's feat/library-base-and-playlist-creation is the largest feature (Library page, Playlist, dialog, carousel, pipes, Firestore service) and is still open. If it doesn't merge before the defence, a chunk of her Sprint 3 work is invisible in the main branch. Mentor should check if it merged by interview date.

Recommended interview angle: One rebuild exercise per student, not a knowledge quiz. For dusixx: implement a loading button (attribute component, signal-driven, no library). For inalitvinka: walk through the three-state auth guard from scratch — draw the state machine, explain why filter + take(1) freezes the router, what happens if Firebase never resolves. Both have enough diary documentation to make questions concrete rather than generic.

Баланс: dusixx берёт больший объём и сложность (179 коммитов, сложная кнопка и система layout), но inalitvinka не сильно отстаёт (158 коммитов) и владеет реальными архитектурными частями: CI/CD с нуля, Firebase Auth с правильным асинхронным гардом, слой данных Firestore. Это полноценная работа двух человек.

Риски для проверки:

  1. Зависимость от библиотек (Taiga UI, angular-split, Firebase SDK): оба студента работают на уровне интеграции для ряда функций. Taiga UI оборачивает многое — обходной путь с MutationObserver для кнопки существует именно потому, что состояние валидации Taiga UI вступило в конфликт. Убедитесь, что они понимают Angular под капотом, а не только поверхность библиотеки.
  2. Выход ngInit: третий студент участвовал в Спринте 1 (layout/header/footer), а затем исчез. Оба оставшихся студента взяли на себя нагрузку и не остановились, однако в ростере есть неурегулированная ситуация. Упомяните это, если ментору нужно проверить официальный статус зачисления.
  3. Риск открытого PR: feat/library-base-and-playlist-creation от inalitvinka — крупнейшая функциональность (страница Library, Playlist, диалог, карусель, пайпы, Firestore-сервис) — всё ещё открыт. Если не будет принят до защиты, значительная часть работы Спринта 3 будет невидима в основной ветке. Ментор должен проверить, был ли он принят к дате интервью.

Рекомендуемый формат интервью: По одному упражнению на перестройку на каждого студента, а не опрос по знаниям. Для dusixx: реализовать кнопку с загрузкой (атрибутный компонент, сигнальное управление, без библиотек). Для inalitvinka: пройти трёхсостояние auth guard с нуля — нарисовать машину состояний, объяснить, почему filter + take(1) замораживает роутер, что произойдёт, если Firebase никогда не разрешится. У обоих достаточно документации в дневниках, чтобы вопросы были конкретными, а не общими.
